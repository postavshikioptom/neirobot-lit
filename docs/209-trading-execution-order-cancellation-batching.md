# Задача 209: Оптимизация массовых отмен (Mass Cancellation Optimization)

## 1. Цель задачи
Снизить потребление лимитов API (Rate Limits) и уменьшить нагрузку на систему в моменты резкой смены стратегии или срабатывания стоп-сигналов, используя эндпоинт `cancel-all` вместо множественных одиночных запросов.

## 2. Инструкции для Gemini по реализации

### А. Изменения в Rust-ядре (API Efficiency)

1.  **Реализация Mass Cancel ([./src/trading/rest_client.rs](./src/trading/rest_client.rs))**:
    *   **Удалить** (или не создавать) метод `cancel_orders_batch(Vec<String>)`, так как в Bybit V5 его нет.
    *   Добавить метод `cancel_all_orders(symbol: &str)`.
    *   Использовать эндпоинт: `POST /v5/order/cancel-all`.
    *   Параметры: `category: "linear"`, `symbol: symbol`.

2.  **Логика принятия решения ([./src/trading/order_manager.rs](./src/trading/order_manager.rs))**:
    *   Внедрить порог `mass_cancel_threshold`.
    *   **Логика**: Если системе требуется отменить более N ордеров одновременно (например, при очистке сетки или экстренном выходе), вместо цикла одиночных `cancel` вызывать один `cancel_all_orders`.
    *   **ВАЖНО**: Учесть, что `cancel-all` атомарен для символа — он отменяет всё. Нужно убедиться, что у бота нет "защитных" ордеров, которые должны остаться.

3.  **Конфигурация ([./src/config/types.rs](./src/config/types.rs))**:
    *   Добавить в `ExchangeConfig`:
        ```rust
        mass_cancel_threshold: usize, // Например, 3. Если отмен > 3, шлем cancel-all.
        ```

### Б. Изменения в Python Lab (Analytics)

1.  **Скрипт анализа**:
    *   Путь: **[./python_lab/scripts/api_limit_analysis.py](./python_lab/scripts/api_limit_analysis.py)**.
    *   **Функционал**: Подсчет экономии "веса" API запросов. По спецификации Bybit 2026, один `cancel-all` тратит меньше лимитов, чем 5–10 одиночных `cancel`.
    *   **Метрика**: `RateLimit_Cost_Savings`.

## 3. Критика и аргументация (По правкам Grok)
*   **Спор об эндпоинте**: Согласен с Grok. Использование несуществующего `cancel-batch` — это критическая ошибка проектирования. Переход на `cancel-all` — единственный легитимный способ массовой очистки стакана на Bybit V5.
*   **Спор о частичном успехе**: Поскольку `cancel-all` либо срабатывает для всех, либо возвращает ошибку, логика обработки "частичного батча" (из первоначального плана) удалена. Это упрощает код и делает его надежнее.
*   **Спор о `Vec<String>`**: Согласен, передача списка ID бессмысленна для Bybit. Мы оперируем понятием "Символ", что идеально ложится в нашу архитектуру "один бот — один символ".

## 4. Ожидаемый результат
Бот мгновенно очищает стакан одним запросом при получении сигнала на смену направления или при остановке. В логах мониторинга фиксируется вызов `action: MASS_CANCEL`, а потребление API лимитов снижается в периоды высокой волатильности.

**Gemini, при реализации в `rest_client.rs`: убедись, что ты правильно обрабатываешь ответ от `cancel-all`. Биржа может вернуть успех, даже если в стакане не было активных ордеров (это нормальное поведение).**
