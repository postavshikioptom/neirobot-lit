# Задача 227: Централизованный репозиторий и GitOps-управление конфигурациями

Переработка задачи с учетом аргументов **Grok** и специфики **HFT-фермы**. Мы переходим от ручной генерации файлов к модели **Infrastructure as Code (IaC)** с поддержкой «горячей» перезагрузки параметров.

## 1. Цель задачи
Создать систему централизованного хранения и дистрибуции конфигураций. Обеспечить 100% консистентность настроек между сотнями ботов через Git-репозиторий и реализовать механизм **Hot Reload** в Rust-ядре.

## 2. Инструкции по реализации для Gemini

### А. Rust: Динамическая конфигурация и Watcher
1.  **Интеграция `notify` ([./src/config/loader.rs](./src/config/loader.rs))**:
    *   Реализовать `ConfigWatcher`, использующий кроссплатформенную библиотеку `notify` для отслеживания изменений в файле `config.toml`.
    *   При обнаружении изменений: выполнить повторную валидацию и **атомарную замену** `Arc<BotConfig>` в памяти.
    *   **Важно**: Разделить параметры на «горячие» (пороги модели, `max_position`, `urgency`) и «статические» (порты, API-ключи), требующие рестарта.

2.  **Валидация как сервис**:
    *   Добавить в `main.rs` флаг `--check-config <PATH>`, который возвращает `0` при успехе или `1` с JSON-ошибкой. Это будет «источник истины» для Python-скриптов.

### Б. Python: Шаблонизатор и Оркестратор ([./scripts/config_manager.py](./scripts/config_manager.py))
1.  **Jinja2 + Hierarchy**:
    *   Реализовать трехуровневое слияние: `defaults.toml` (общие) -> `group_scalping.toml` (групповые) -> `BTCUSDT.toml` (специфичные для тикера).
    *   Использовать **Jinja2** для подстановки переменных (например, расчет плеча на основе волатильности).

2.  **GitOps Workflow**:
    *   Скрипт должен уметь делать `git pull` перед генерацией и `git commit/push` после валидации.
    *   **Diff Preview**: Перед применением изменений выводить `diff` в терминал (библиотека `rich` или `difflib`).

3.  **Безопасность**:
    *   Шаблоны не должны содержать сырых ключей. Секреты подставляются только в формате `ENC:...` из защищенного окружения (задача 216).

## 3. Спорные моменты и аргументация

-   **Против S3 (в ответ Grok)**: Я не согласен с обязательным использованием S3 для старта. Git дает нативный аудит, историю коммитов и `diff` из коробки. Для фермы до 500 ботов Git-pull на старте эффективнее и проще в отладке.
-   **Против дублирования схем**: Gemini должна использовать вызов Rust-бинарника с флагом `--check-config`. Любая попытка описать схему на Pydantic в Python приведет к рассинхрону при добавлении полей в Rust-структуры.
-   **Hot Reload**: Согласен с Grok, что это критично. В HFT нельзя терять WebSocket-сессию и L2-кеш только потому, что мы решили изменить `stop_loss` на 2 базисных пункта.

## 4. Ожидаемый результат
1.  Изменение одного файла в Git-репозитории автоматически доставляется на все инстансы.
2.  Боты подхватывают изменения «на лету» без разрыва торговых сессий.
3.  Любая ошибка в конфиге блокирует деплой на этапе валидации в Python, не затрагивая работающие процессы.

## 5. Необходимые зависимости
-   **Rust**: `notify = "6.1"`, `arc-swap = "1.7"`.
-   **Python**: `jinja2`, `gitpython`, `rich`.
