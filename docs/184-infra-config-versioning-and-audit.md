# **Задача №184: Версионирование и аудит конфигураций (Config Versioning and Audit)**

**Цель**: Обеспечение воспроизводимости результатов и отслеживание изменений в параметрах ботов. Реализация системы автоматического резервного копирования `config.toml`, вычисления контрольных сумм (SHA-256) и логирования изменений (diff) при перезагрузке конфига по сигналу `SIGHUP`.

---

## **План реализации для Gemini AI Coder:**

### **1. Изменения в [Cargo.toml](./Cargo.toml)**
Добавить библиотеки для хеширования и сравнения текстов:
```toml
sha2 = "0.10"   # Для вычисления хэша конфига
diffy = "0.3"  # Для генерации читаемого diff при перезагрузке
```

### **2. Управление в [./deploy/manage.sh](./deploy/manage.sh)**
Реализовать атомарное обновление и аудит:
- **Backup**: Перед заменой `config.toml` в папке бота создавать резервную копию в `bots/SYMBOL/config_history/config.toml.$(date +%Y%m%d_%H%M%S).bak`.
- **Security**: Устанавливать права `chmod 600` на файлы конфигурации и бэкапы (чтение/запись только владельцу `neirobot`).
- **Atomic Update**: Сначала копировать новый файл в `config.toml.tmp`, затем выполнять `mv config.toml.tmp config.toml`, чтобы избежать чтения недозаписанного файла.

### **3. Обработка сигналов в [./src/run-bot.rs](./src/run-bot.rs)**
Внедрить асинхронную обработку `SIGHUP` (через `tokio::signal`):
- **Signal Loop**: Запустить `tokio::spawn`, который слушает `SIGHUP`.
- **Action**: При получении сигнала вызывать `config::load()`, вычислять новый хэш и сравнивать с предыдущим.
- **Audit Log**: При старте и каждой перезагрузке выводить хэш: `[Audit] Config SHA-256: 8f3a2b...`.

### **4. Логика сравнения в [./src/config/loader.rs](./src/config/loader.rs)**
Реализовать детекцию изменений:
- **Hashing**: Метод вычисления хэша файла `SHA-256`.
- **Diffing**: Если хэш изменился, использовать `diffy` для сравнения старого и нового содержимого файла. Выводить в лог только изменившиеся строки: `[Audit] Config changed: -maker_offset = 1.0, +maker_offset = 1.5`.

### **5. Тестирование и валидация**
- **SIGHUP Mock**: В [./tests/risk_gates.rs](./tests/risk_gates.rs) симулировать отправку `SIGHUP` процессу и проверить появление в логах записи `[Audit] Config SHA-256`.
- **Diff Test**: Изменить один параметр в файле и убедиться, что в логах отобразился корректный `diff` без перезапуска всего приложения.
- **Permissions Check**: Убедиться, что `manage.sh` корректно выставляет права `600` на создаваемые бэкапы.

## **Аргументы и обоснование (согласовано с Grok):**
1. **Отмена Git в рантайме**: Согласен с Grok, использование Git внутри `bots/` излишне и опасно из-за наличия там логов и тяжелых моделей. Простой бэкап в `config_history/` — более надежное решение для продакшена.
2. **Атомарность**: Операция `mv` в Linux является атомарной. Это гарантирует, что `run-bot` никогда не прочитает файл в промежуточном состоянии во время деплоя.
3. **Хэширование (SHA-256)**: Контрольная сумма в логах — единственный способ сопоставить торговые данные с конкретными настройками при последующем анализе в `python_lab`.
4. **SIGHUP Reload**: Позволяет менять параметры "на лету" (например, `max_position_size`) без разрыва WebSocket-сессий и потери ликвидности в стакане, что критично для HFT.
5. **Security**: Конфиги содержат риск-параметры. Ограничение прав `chmod 600` — базовый уровень защиты от несанкционированного доступа других пользователей системы.
