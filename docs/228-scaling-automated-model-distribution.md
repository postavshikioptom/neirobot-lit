# Задача 228: Автоматизированная дистрибуция и безопасный Hot-Swap моделей


## 1. Цель задачи
Реализовать конвейер доставки весов моделей (`.onnx`) с поддержкой выборочного обновления, автоматического отката (Rollback) при ошибках и «горячей» замены сессии инференса без остановки торгового цикла.

## 2. Инструкции по реализации для Gemini

### А. Python: Умный деплой ([./scripts/model_manager.py](python_lab/scripts/model_manager.py))
1.  **Selective Deploy**:
    *   Реализовать аргументы `--symbols BTC,ETH` и `--group scalping` (фильтрация по тегам в `farm.yaml`).
    *   **Atomic Push**: Сначала копировать `model.onnx.tmp`, затем атомарно переименовывать в `model.onnx` + обновлять текстовый файл `model.hash`.
2.  **Backup**: Перед обновлением копировать текущую модель в `model.onnx.bak`.

### Б. Rust: Модуль инференса с отказоустойчивостью ([./src/ml/onnx_engine.rs](./src/ml/onnx_engine.rs))
1.  **Trigger & Watcher**:
    *   Использовать `notify` для отслеживания файла `model.hash` (избегаем гонки при копировании большого `.onnx`).
    *   Добавить поддержку сигнала `SIGUSR1` для принудительного триггера загрузки.
2.  **Safety Cycle (Hot Swap)**:
    *   Проверять флаг `enable_model_hotswap` в `BotConfig`.
    *   **Warmup**: После загрузки новой сессии прогнать 100 циклов инференса на dummy-данных.
    *   **Auto Rollback**: Если `Warmup` выдал ошибку или средняя латентность инференса выросла более чем на 50% относительно старой модели — немедленно отменить замену и загрузить `.bak`.
3.  **Memory Management**:
    *   Использовать `ArcSwap<OrtSession>`.
    *   Для предотвращения утечек в GPU/C-API: после свопа явно вызывать `drop()` старой сессии, убедившись, что счетчик ссылок `Arc::try_unwrap` позволяет это (или через слабые ссылки).
4.  **Monitoring**: Отправлять алерты через `AlertManager` (задача 222) о статусе (Success/Rollback) и обновлять Prometheus gauge `model_version_timestamp`.

## 3. Спорные моменты и аргументация

*   **Против массового деплоя (`--all`)**: Согласен с Grok. Одновременное обновление 100+ ботов новой моделью — это системный риск. Селективный деплой позволяет проводить Canary-тесты.
*   **Против простого File Watch**: Grok прав, наблюдение за `.onnx` опасно, так как файл может быть еще не до конца записан. Наблюдение за маленьким `model.hash`, который пишется *после* модели — стандарт надежности.
*   **Rollback по латентности**: Это критическое требование. Модель может быть валидной по весам, но «тяжелой» для текущего CPU/GPU, что убьет HFT-тайминги. Бот обязан это детектировать.
*   **Memory Leak**: ONNX Runtime при частых перезагрузках сессий может фрагментировать память. Важно контролировать жизненный цикл `OrtEnv` и `OrtSession`.

## 4. Ожидаемый результат
1.  Безопасное обновление интеллекта бота без разрыва WebSocket-соединений.
2.  Автоматическая защита от «битых» или слишком медленных моделей.
3.  Полный аудит версий в логах и мониторинге.
