# **Задача №179: Лимит времени на неисполненные ордера (Unfilled Order Time Limit)**

**Цель**: Предотвращение нахождения "зависших" (stale) лимитных ордеров в стакане, которые могут стать токсичными при изменении рыночной конъюнктуры. Бот должен автоматически отменять или переставлять ордера, которые не были исполнены в течение заданного окна `max_order_life_ms`.

---

## **План реализации для Gemini AI Coder:**

### **1. Изменения в [./src/config/types.rs](./src/config/types.rs)**
Добавить параметры контроля времени жизни ордеров в `RiskConfig` (изоляция **per-bot**):
- **`max_order_life_ms`**: `u64` (максимальное время жизни, например 30000мс).
- **`stale_order_action`**: `enum { CancelOnly, CancelAndMarketFill, Repeg }`.
- **`min_fill_pct_to_keep`**: `f64` (порог частичного исполнения, например 0.8, выше которого ордер не отменяется).
- **`stale_check_interval_ms`**: `u64` (интервал работы фонового проверяльщика, например 1000мс).

### **2. Состояние в [./src/trading/order_manager.rs](./src/trading/order_manager.rs)**
- Использовать `active_intents: HashMap<String, OrderIntent>` из задачи [176](./docs/000-tasks_list.md).
- Убедиться, что `OrderIntent` содержит:
    - `created_at: u64` (локальный таймстамп создания).
    - `qty: f64` (изначальный объем).
    - `filled_qty: f64` (обновляется в реальном времени по фидам из задачи [064](./docs/000-tasks_list.md)).

### **3. Логика в [./src/risk/health_monitor.rs](./src/risk/health_monitor.rs)**
Реализовать метод `check_stale_orders()`, вызываемый периодически из `run-bot.rs`:
- **Итерация по интентам**: Пройти по всем активным `order_link_id` в `OrderManager`.
- **Условие срабатывания**: `if now - intent.created_at > config.max_order_life_ms`.
- **Проверка Fill-порога**: Если `intent.filled_qty / intent.qty < config.min_fill_pct_to_keep`:
    - **CancelOnly**: Вызвать `order_manager.cancel_order()`.
    - **CancelAndMarketFill**: 
        - Проверить свежесть текущего сигнала (задача [169](./docs/000-tasks_list.md)): `if now - signal.ts < config.max_signal_age_ms`.
        - Если сигнал свежий — отправить `MarketOrder` на `remaining_qty`, затем отменить лимит.
    - **Repeg**: Инициировать перестановку к `best_bid/ask` (задача [108](./docs/000-tasks_list.md)), сохраняя при этом исходный `created_at` (для предотвращения вечного чейзинга).
- **Cleanup**: Обязательно вызывать `remove_intent()` после завершения действия, чтобы освободить место для новых ордеров (связь с [176](./docs/000-tasks_list.md)).

### **4. Запуск в [./src/run-bot.rs](./src/run-bot.rs)**
- Запустить `tokio::task` с `tokio::time::interval(stale_check_interval_ms)` после инициализации бота.

### **5. Тестирование в `tests/health_monitor_integration.rs`**
- **Timeout Test**: Выставить ордер (mock intent) -> "прокрутить" время -> Убедиться в вызове отмены.
- **Market Fill Test**: Симулировать таймаут при свежем сигнале -> Убедиться в генерации Market-ордера.
- **Persistence Test**: Убедиться, что при `fill_pct = 0.9` (выше порога) ордер остается в стакане.

## **Аргументация (согласовано с Grok):**
1. **Интеграция с Интентами**: Использование `active_intents` из задачи 176 — наиболее эффективный способ, так как там уже есть вся мета-информация об ордере (цена, объем, время).
2. **Signal Awareness**: Принудительный выход по рынку (`MarketFill`) допустим только если сигнал модели всё еще актуален (задача 169). Это предотвращает "удары по рынку" в моменты, когда прогноз уже изменился.
3. **Double-Dip Prevention**: Удаление интента (`remove_intent`) после таймаута критично. Без этого гейт дубликатов из задачи 176 будет блокировать новые попытки входа на том же уровне.
4. **Hysteresis**: Сохранение оригинального `created_at` при `Repeg` ограничивает общее время нахождения бота в сделке, предотвращая "залипание" в бесконечных попытках переставить ордер за улетающей ценой.

**Gemini, твоя задача — следить за тем, чтобы ликвидность бота не "протухала" в стакане. Ордер должен либо исполниться быстро, либо исчезнуть.**
