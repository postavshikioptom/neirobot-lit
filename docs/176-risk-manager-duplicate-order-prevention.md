# **Задача №176: Защита от дублирования ордеров (Duplicate Order Prevention)**

**Цель**: Предотвращение случайного открытия избыточных позиций из-за повторной отправки идентичных ордеров. Бот должен использовать клиентские ID для идемпотентности и "мягкую" (fuzzy) проверку параметров ордера, чтобы отличить новое торговое намерение от ошибочного дубликата.

---

## **План реализации для Gemini AI Coder:**

### **1. Изменения в [./src/config/types.rs](./src/config/types.rs)**
Добавить параметры в структуру `RiskConfig`:
- **`duplicate_window_ms`**: `u64` (окно детекции, например 5000мс).
- **`duplicate_qty_tolerance_pct`**: `f64` (допуск по объему, например 0.01 для 1%).
- **`duplicate_price_tolerance_ticks`**: `u32` (допуск по цене в тиках).
- **`order_intent_timeout_ms`**: `u64` (таймаут очистки "зависших" интентов, например 30000мс).

### **2. Генерация `order_link_id` в [./src/trading/order_manager.rs](./src/trading/order_manager.rs)**
Обеспечить уникальность ID для идемпотентности Bybit V5:
- **Механизм**: Добавить в `OrderManager` атомарный счетчик `nonce: AtomicU64`.
- **Формат**: `{bot_id}-{signal_id}-{unix_ms}-{nonce}`. 
- **Логика**: Каждый новый ордер получает уникальный ID. При `amend` (задача [103](./docs/000-tasks_list.md)) использовать старый ID или добавлять суффикс `-v2`.

### **3. Состояние в [./src/risk/risk_manager.rs](./src/risk/risk_manager.rs)**
Реализовать хранилище активных намерений:
- **Поля**: `active_intents: HashMap<String, OrderIntent>` (ключ — `order_link_id`).
- **Структура `OrderIntent`**: `side`, `price`, `qty`, `timestamp`.
- **Fuzzy Matching**: Метод `is_duplicate(side, price, qty)`:
    - Итерировать по `active_intents`.
    - **Duplicate**, если:
        1. Та же сторона (`side`).
        2. `abs(new_qty - old_qty) / old_qty < duplicate_qty_tolerance_pct`.
        3. `abs(new_price - old_price) < tick_size * duplicate_price_tolerance_ticks`.
        4. `now - old_ts < duplicate_window_ms`.

### **4. Жизненный цикл и Cleanup**
- **Добавление**: При вызове `place_order` регистрировать интент в `RiskManager`.
- **Удаление**: По сигналам WebSocket (задача [064](./docs/000-tasks_list.md)) об исполнении или отмене.
- **Timeout Cleanup**: В [./src/risk/health_monitor.rs](./src/risk/health_monitor.rs) реализовать периодическую очистку интентов, чей возраст `> order_intent_timeout_ms` (защита от потери WS-сообщений).

### **5. Тестирование в [./tests/risk_gates.rs](./tests/risk_gates.rs)**
- **Fuzzy Match Test**: Отправить ордер -> Отправить второй с ценой, измененной на 0.5 тика. Убедиться, что второй блокируется как дубликат.
- **Idempotency Test**: Убедиться, что `order_link_id` содержит инкрементальный `nonce`.
- **Amend Test**: Проверить, что обновление ордера (amend) по существующему `link_id` не считается дубликатом самого себя.

## **Аргументация (согласовано с Grok):**
1. **Fuzzy Logic**: Строгое сравнение цены и объема неэффективно для HFT, так как микро-изменения (например, из-за округления или ре-пеггинга) могут обойти защиту. Допуски в 1% и несколько тиков делают защиту надежной.
2. **Atomic Nonce**: Добавление `nonce` в `order_link_id` гарантирует уникальность даже при генерации нескольких ордеров в течение одной миллисекунды (что реально для высокочастотного Rust-ядра).
3. **Intent Persistence**: Хранение интентов в `HashMap` по ID позволяет быстро обрабатывать ответы биржи, а фоновая очистка в `health_monitor` предотвращает утечки памяти и ложные блокировки при сбоях сети.
4. **Side & Strategy**: Параметр `allow_multiple_active_orders` позволяет боту выставлять сетку, если это разрешено конфигом, не считая разные ценовые уровни дубликатами.
