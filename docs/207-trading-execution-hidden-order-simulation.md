# Задача 207: Симуляция и реализация скрытых ордеров (Iceberg Orders)

## 1. Цель задачи
Реализовать клиентскую эмуляцию **Iceberg-ордеров** для скрытия крупных позиций. Бот должен выставлять в стакан только малую рандомизированную часть объема, автоматически «подкладывая» ликвидность (refill) по мере исполнения, при условии, что цена остается в допустимом диапазоне.

## 2. Инструкции для Gemini по реализации

### А. Изменения в Rust-ядре (Execution & Protection)

1.  **Расширение стратегий ([./src/trading/execution.rs](./src/trading/execution.rs))**:
    *   Добавить в `ExecutionStrategy` (из задачи 206) вариант: `Iceberg { total_size: f64, display_ratio: f64 }`.
    *   `total_size` — неизменяемый целевой объем, `display_ratio` — базовый процент для отображения.

2.  **Конфигурация ([./src/config/types.rs](./src/config/types.rs))**:
    *   Расширить `SorConfig` (введенный в задаче 206), **не создавая новый**:
        ```rust
        // В составе SorConfig
        iceberg_randomize: f32,    // Коэффициент вариации display_ratio (0.0 - 0.5)
        iceberg_price_dev_bps: u32, // Макс. отклонение цены от начальной для продолжения рефилла
        ```

3.  **Логика Refill и защиты ([./src/trading/order_manager.rs](./src/trading/order_manager.rs))**:
    *   При полном исполнении «плеча» айсберга:
        1.  Рассчитать новый `display_size` с учетом `iceberg_randomize` (каждый раз новое значение).
        2.  **Проверка цены**: Сравнить текущий `mid_price` с ценой первого плеча. Если отклонение > `iceberg_price_dev_bps` — **прекратить выполнение (Abort)** и уведомить систему.
        3.  Отправить новый лимитный ордер на остаток или на следующий лот.

### Б. Изменения в Python Lab (Analytics)

1.  **Скрипт анализа**:
    *   Путь: **[./python_lab/scripts/iceberg_analyzer.py](./python_lab/scripts/iceberg_analyzer.py)**.
    *   **Функционал**: Сравнение эффективности айсбергов с агрессивным исполнением из задачи 204.
    *   **Метрика**: «Time to invisibility» — через какое время после начала работы айсберга стакан начинает «убегать» (корреляция с `total_size`).

## 3. Критика и аргументация (По правкам Grok)
*   **Спор о структуре данных**: Согласен с Grok. Передача `remaining_size` в Enum — плохая практика, так как это изменяемое состояние. Правильнее хранить `total_size` и вычислять остаток на основе исполненных `fills`.
*   **Спор о конфигурации**: Расширение `SorConfig` вместо создания нового файла логично, так как Айсберг — это подвид тактики SOR.
*   **Спор об отмене (Abort)**: Это критическое замечание. Без логики отмены при уходе цены бот превратится в «дойную корову» для других участников, которые будут выкупать его скрытую ликвидность по невыгодной цене.

## 4. Ожидаемый результат
Бот может исполнять ордера объемом в 5-10 раз больше обычного объема уровня стакана, не вызывая немедленного панического движения цены. В `market_impact.csv` (задача 204) должен фиксироваться суммарный импакт на весь `total_size` айсберга.

---
**Gemini, при реализации рефилла в `order_manager.rs`: используй `f64::min(calculated_display, remaining_total)`, чтобы не выставить лишний объем на последнем шаге.**
