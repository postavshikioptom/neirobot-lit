# Задача 094: Поддержка Memmap и Lazy Loading для больших датасетов

**Цель**: Реализовать эффективную загрузку данных, позволяющую обучать модели на датасетах, превышающих объем RAM (100ГБ+), используя нативный Memory Mapping в Parquet и потоковую передачу (Streaming).

## 1. Изменения в Python-лаборатории ([./python/](./python/))

### 1.1. Обновление `dataset.py`
*   **Режимы загрузки (Data Modes)**: Реализовать три стратегии в `LOBDataset`:
    1.  **In-Memory**: Стандартная загрузка всех данных в RAM (для малых сетов).
    2.  **Streaming (Lazy)**: Использование `polars.scan_parquet(memory_map=True)` + `.collect_streaming()`. Позволяет читать Parquet-файлы "на лету" с сохранением сжатия (Snappy/Zstd).
    3.  **Binary Memmap**: Опциональная конвертация в **uncompressed raw binary** (через `np.memmap`) для максимально быстрого случайного доступа (Random Access), если позволяет место на диске.
*   **Индексация**: Для Lazy-режимов реализовать индексную карту (массив смещений), чтобы `__getitem__` мог мгновенно находить нужную строку в файле без перебора.

### 1.2. Обновление `train.py`
*   **Аргументы CLI**:
    *   `--data_mode`: `[memory, streaming, memmap]` (по умолчанию `memory`).
    *   `--cache_dir`: Путь для хранения временных бинарных файлов (для режима `memmap`).
*   **Валидация ресурсов**: При запуске использовать `psutil` для проверки доступной RAM. Если `dataset_size > available_ram * 0.7`, выводить `warning` и предлагать переключиться на `streaming`.

## 2. Почему это важно (Аргументы Grok):
*   **Parquet Native Memmap**: Parquet — это колоночный формат. `PyArrow` позволяет маппить только нужные колонки (Price, Vol), не считывая остальное, что экономит RAM без создания огромных `.npy` файлов.
*   **Disk Space**: Прямая конвертация в сырой бинарный формат может увеличить размер данных в 3-5 раз. Потоковое чтение Parquet (Streaming) — лучший баланс между скоростью и местом.
*   **Zero-copy**: `polars` и `pyarrow` обеспечивают zero-copy доступ к данным, что минимизирует накладные расходы на `memcpy` при формировании батчей.

## 3. Критические требования
*   **Thread Safety**: При использовании `streaming` в `DataLoader` (multi-processing), каждый воркер должен иметь свой файловый дескриптор, чтобы избежать блокировок.
*   **Shape Consistency**: Тензоры, считанные через `memmap`, должны сохранять форму `(Channels, Levels, Time)`.
*   **Performance**: Режим `streaming` может быть медленнее на 20-30%. Это допустимая цена за возможность обучения на "бесконечных" данных.

## 4. Тестирование
*   **OOM Stress Test**: Попытка запустить обучение на датасете, в 2 раза превышающем RAM, в режиме `streaming`. Бот должен работать стабильно.
*   **Parity Check**: Убедиться, что `loss` и `metrics` идентичны при обучении в `memory` и `streaming` режимах на одном и том же малом датасете.

## 5. Задача 094-2: Исправление поддержки Multi-Horizon в Streaming/Memmap режимах

**Проблема**: 
При реализации задачи **160 (Multi-Horizon Label Generation)** флаг `self.is_multi_horizon` и сопутствующая логика инициализации меток были добавлены только в метод `_init_memory_mode`. В режимах `streaming` и `memmap` этот атрибут не создается, что приводит к `AttributeError: 'LOBDataset' object has no attribute 'is_multi_horizon'` при вызове `__getitem__` (например, во время проверки данных на NaN в `train.py`). Также обнаружены NaN-значения при проверке данных, что требует верификации логики нормализации в этих режимах.

**План исправления**:
1.  **Рефакторинг `LOBDataset.__init__`**:
    *   Вынести определение `self.is_multi_horizon` и `self.num_horizons` в общий блок конструктора `__init__`, до вызова специфичных методов `_init_*`.
    *   Логика определения должна быть универсальной: проверять наличие колонок `label_h*` в схеме (через `pl.scan_parquet(...).collect_schema()` для lazy-режимов или `df.columns` для memory).
2.  **Унификация `_init_streaming_mode` и `_init_memmap_mode`**:
    *   Обеспечить корректную инициализацию `self.labels` и `self.vols` с учетом `is_multi_horizon`.
    *   В `streaming` режиме убедиться, что `label_cols` подхватывают все горизонты для формирования батча в кэше.
3.  **Исправление `__getitem__`**:
    *   Убедиться, что логика формирования `y` (метки) и `v` (волатильности) корректно обрабатывает размерности для multi-horizon во всех режимах.
4.  **Расследование причин NaN**:
    *   Проверить, не возникают ли NaN при расчете `past_returns` или `imbalance` в режиме `streaming`.
    *   Добавить защитные проверки (`fill_null(0.0)`) в пайплайн формирования признаков внутри `LOBDataset`.

## 6. Результаты выполнения Задачи 094-2
*   **Унифицированная инициализация**: Обнаружение горизонтов (`label_h*`) вынесено в начало `__init__`, что устранило `AttributeError: is_multi_horizon` во всех режимах (`memory`, `streaming`, `memmap`).
*   **Поддержка Multi-Horizon в Streaming**: Рефракторинг `_init_streaming_mode` и `_getitem_streaming` обеспечил корректное формирование батчей меток для всех горизонтов.
*   **Валидация Memmap**: В метаданные кэша добавлена проверка на состав колонок меток и длину последовательности, что предотвращает использование неактуального кэша.
*   **Защита от NaN**: 
    *   Внедрен `fill_null(0.0)` в пайплайне Polars для `streaming` режима.
    *   Добавлена финальная обработка `np.nan_to_num(0.0)` в `_process_sample`, что гарантирует отсутствие NaN в тензорах признаков.
*   **Типизация меток**: Исправлено приведение меток к `torch.LongTensor` во всех режимах, что критично для функции потерь `CrossEntropyLoss`.
