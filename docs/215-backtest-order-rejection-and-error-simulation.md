# Задача 215: Симуляция отказов и ошибок ордеров (Order Rejection and Error Simulation)

## 1. Цель задачи
Реализовать в бэктестере механизм симуляции негативных ответов от биржи (Bybit V5). Это необходимо для тестирования устойчивости `OrderManager` и логики риск-менеджмента к техническим сбоям, а также для валидации алгоритмов повторных попыток (Retries) с экспоненциальной задержкой.

## 2. Инструкции для Gemini по реализации

### А. Модель ошибок (Error Simulator)
1.  **Создать файл `./python_lab/src/backtest/error_sim.py`**:
    *   Реализовать класс `ExchangeErrorSimulator` с использованием `numpy.random.default_rng(seed)` для детерминированного воспроизведения ошибок.
    *   **Типы ошибок (Bybit V5 Codes)**:
        *   `RateLimitError` (Код 10006 / 429): Имитация превышения лимитов.
        *   `OrderRejection` (Коды 10001, 20001): Отказы по разным причинам.
        *   `Timeout / Unknown`: Ситуация, когда статус ордера неясен (сетевой лаг).
    *   **Параметры**: Вероятности ошибок задаются в Python-конфигурации бэктеста (не в `BotConfig`).
    *   **Data Source**: Если доступен `execution_quality.csv` или `bot.log`, использовать их как опциональный источник для калибровки вероятностей, в противном случае — использовать `default_rejection_rate = 0.0001`.

### Б. Логика восстановления (Retry & Backoff)
1.  **Портирование Rust-логики**:
    *   Реализовать в бэктестере поведение, идентичное задачам 085 и 234: при получении `RateLimitError` стратегия должна применять **Exponential Backoff** (экспоненциальное увеличение паузы перед следующей попыткой).
2.  **Интеграция в движок**:
    *   Обновить `./python_lab/src/backtest/engine.py`. Перед каждой операцией с API вызывать `simulator.should_fail()`.
    *   При возникновении ошибки генерировать событие `ExchangeErrorEvent`.

### В. Аналитика и Валидация
1.  **Метрики**:
    *   `Error_Recovery_Time`: Время от возникновения ошибки до восстановления нормальной торговли.
    *   `Lost_Trades_Count`: Количество сигналов, пропущенных из-за технических сбоев.
2.  **Тестирование**:
    *   Создать `./python_lab/tests/test_error_recovery.py`.
    *   **Кейс**: Проверить, что при получении серии 429 ошибок бэктестер корректно увеличивает интервал между запросами согласно алгоритму Backoff.

## 3. Критика и аргументация (По правкам Grok)
*   **Спор о парсинге логов**: Согласен с Grok. Автоматический парсинг `bot.log` слишком хрупок из-за сложности форматов `tracing`. Делаем его опциональным, приоритет — дефолтным вероятностям и ручной настройке.
*   **Спор о Backoff**: Это критически важное замечание. Бэктест должен проверять не только факт ошибки, но и **правильность реакции** на неё. Если в Rust-ядре заложен экспоненциальный откат, бэктест обязан его имитировать, иначе результаты будут ложными.
*   **Спор о воспроизводимости**: Использование `numpy.random.default_rng` с фиксацией `seed` обязательно. Мы должны иметь возможность повторить «плохой» прогон для отладки конкретного сбоя.

## 4. Ожидаемый результат
Бэктестер выдает отчет о «Resilience Score» (оценка живучести). Мы получаем ответ на вопрос: «Насколько упадет наш PnL, если биржа начнет отклонять 0.1% наших запросов и вводить штрафные задержки за лимиты?».
