# Задача 214: Монте-Карло симуляция вариативности задержек (Latency Perturbation)

## 1. Цель задачи
Реализовать систему стресс-тестирования стратегии путем многократного прогона бэктеста с внесением случайного «джиттера» (jitter) в задержки исполнения. Это позволит оценить устойчивость прибыли к нестабильности сети и лагам биржи.

## 2. Инструкции для Gemini по реализации

### А. Модель распределения задержек
1.  **Создать файл `./python_lab/src/backtest/perturbation.py`**:
    *   Использовать `scipy.stats.lognorm` для генерации задержек (логнормальное распределение — стандарт для сетевых лагов).
    *   **Источник параметров**:
        *   Если файл `execution_quality.csv` (задача 202) существует — рассчитать `mean` и `std` по реальным данным.
        *   **Fallback (обязательно)**: Если файла нет, использовать дефолтные параметры HFT-среды: `mean = 20ms`, `std = 15ms`.
    *   Реализовать генератор с использованием `numpy.random.default_rng(seed)` для обеспечения воспроизводимости результатов.

### Б. Параллельный Monte Carlo Runner
1.  **Создать файл `./python_lab/scripts/monte_carlo_backtest.py`**:
    *   **Интеграция**: Импортировать `EventEngine` из `./python_lab/src/backtest/engine.py`. Не дублировать код движка.
    *   **Параллелизация**: Использовать `multiprocessing.Pool` для распределения $N$ итераций (например, 100) по ядрам CPU.
    *   **Worker Function**: Функция-воркер должна инициализировать движок, применять уникальный набор задержек к каждому `OrderEvent` и возвращать итоговый PnL и Drawdown.

### В. Аналитика и Визуализация
1.  **Использование Matplotlib/Seaborn**:
    *   Построить гистограмму распределения PnL по итогам всех итераций.
    *   Построить «кривую устойчивости» (PnL в зависимости от 95-го перцентиля задержки).
2.  **Метрики**:
    *   **PnL at Risk (5th percentile)**: Худший ожидаемый результат при «плохой» сети.
    *   **Reliability Score**: Процент итераций, оставшихся в прибыли.

### Г. Зависимости и Тесты
1.  **Requirements**: Добавить `scipy` и `matplotlib` в `./python_lab/requirements.txt`.
2.  **Тестирование**: Создать `./python_lab/tests/test_monte_carlo.py` для проверки, что при одинаковом `seed` результаты итераций идентичны.

## 3. Критика и аргументация (По правкам Grok)
*   **Спор о Numba**: Полностью согласен. Использование Numba на уровне всего Event Loop внутри Multiprocessing создаст избыточную нагрузку на сериализацию и конфликты GIL. Оставляем Numba только для внутренних математических функций матчинга (если они выделены).
*   **Спор о CSV**: Fallback на дефолтные параметры задержек (20/15ms) делает инструмент полезным даже на этапе разработки, когда реальных данных от Rust-бота еще нет.
*   **Спор об RNG**: Использование `default_rng` — современный стандарт NumPy, заменяющий старый `np.random.seed`, что критично для безопасности потоков.

## 4. Ожидаемый результат
