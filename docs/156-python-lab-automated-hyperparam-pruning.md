# Задача №156: Автоматическое отсечение (Pruning) в Optuna

Согласно [./docs/000-architecture.md](./docs/000-architecture.md), обучение моделей LiT на данных стакана требует больших ресурсов. Внедрение механизмов **Pruning** в Optuna позволит отсекать бесперспективные конфигурации на ранних этапах, высвобождая время для более качественного поиска гиперпараметров.

## План реализации для Gemini AI Coder:

### 1. Расширение CLI в [./python_lab/scripts/train.py](./python_lab/scripts/train.py)
Добавить поддержку различных стратегий отсечения:
- **`--pruner_type`**: выбор между `median` (базовый), `hyperband` (бюджетирование ресурсов) и `patience` (устойчивость к шуму).
- **Параметры ресурса**: 
    - `--min_resource` и `--max_resource` для `HyperbandPruner` (количество эпох).
    - `--n_startup_trials` (минимум 20): количество полных триалов перед включением логики отсечения.
    - `--n_warmup_steps` (минимум 25): количество эпох, которые модель должна пройти до первой проверки на отсечение.
- **Sampler**: Убедиться, что по умолчанию используется `optuna.samplers.TPESampler`.

### 2. Реализация Objective Function
Настроить `study` на максимизацию основной метрики:
- **Direction**: `optuna.create_study(direction='maximize', ...)`.
- **Primary Metric**: Использовать **MCC** (задача 051) как основной показатель качества.

### 3. Интеграция в тренировочный цикл
В [./python_lab/scripts/train.py](./python_lab/scripts/train.py) внутри цикла по эпохам реализовать взаимодействие с Optuna:
```python
# Логика для Gemini
for epoch in range(epochs):
    train_score = train_one_epoch(...)
    val_mcc = validate(...) # Расчет MCC на валидации
    
    # Репортим промежуточный результат
    trial.report(val_mcc, step=epoch)
    
    # Проверка на отсечение
    if trial.should_prune():
        logger.info(f"Trial {trial.number} pruned at epoch {epoch}")
        raise optuna.exceptions.TrialPruned()
```

### 4. Обработка "шумных" метрик (LOB Specific)
Учитывая высокую волатильность **MCC** на данных стакана:
- При использовании `PatiencePruner` задать параметр `patience` (количество шагов без улучшения), чтобы не отсекать перспективные модели из-за случайной просадки на одной эпохе.
- Установить повышенные значения `n_startup_trials` (20+) и `n_warmup_steps` (25+), чтобы дать трансформеру "прогреться" и стабилизировать градиенты.

### 5. Логирование и статистика в [./python_lab/src/utils.py](./python_lab/src/utils.py)
Использовать встроенные средства Optuna для итогового отчета:
- Выводить `len(study.get_trials(states=[TrialState.PRUNED]))` для оценки агрессивности прунера.
- Анализировать "среднюю эпоху отсечения", чтобы понять, насколько рано мы ловим плохие модели.

## Аргументация (Спор с Grok):
- **Согласен**: Добавление `PatiencePruner` критично для LOB, так как MCC — "шумная" метрика по сравнению с Loss, и обычный `MedianPruner` может быть слишком агрессивным.
- **Согласен**: Высокие значения `n_warmup_steps` необходимы. Трансформеры часто начинают сходиться только после 10-20 эпох, и раннее отсечение убьет потенциально лучшие конфигурации.
- **Согласен**: `TPESampler` и `direction='maximize'` для MCC — это база, которую нужно закрепить в коде.
