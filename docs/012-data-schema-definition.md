# 012 - Data Schema Definition

Цель задачи: Создать жёсткий стандарт схемы Parquet-файлов для сырых снимков стакана (LOB snapshots). Это «контракт» проекта: Rust-модуль dump.rs пишет данные строго по этой схеме, а Python-скрипт dataset.py читает их. Мы фиксируем 50 уровней стакана с чередованием цены и объема.

Файл для создания: docs/data_schema.json

```json
{
  "format": "parquet",
  "version": "1.0",
  "description": "Raw LOB Snapshot Schema for LiT Model (top-50 levels, Bybit orderbook.50). Compression: SNAPPY or ZSTD recommended.",
  "columns": [
    "timestamp_ms",
    "last_update_id",
    "ask_p_0", "ask_v_0",
    "ask_p_1", "ask_v_1",
    "ask_p_49", "ask_v_49",
    "bid_p_0", "bid_v_0",
    "bid_p_1", "bid_v_1",
    "bid_p_49", "bid_v_49"
  ],
  "types": {
    "timestamp_ms": "uint64",
    "last_update_id": "uint64",
    "ask_p_*": "float32",
    "ask_v_*": "float32",
    "bid_p_*": "float32",
    "bid_v_*": "float32"
  },
  "notes": "Total columns: 2 + 200 = 202. Index 0 = best price. Interleaved price/volume pairs."
}
```

## ML Tensor Structure (Derived Features)

Перед подачей в модель LiT, данные из Parquet преобразуются в 3-канальный тензор. Эти признаки вычисляются "на лету" и не хранятся в файлах.

**Shape одного снимка:** `(3, 50)` (Каналы, Уровни)

1. **Канал 0: Normalized Price**
   * Формула: `(p - mid) / mid` (агрегированное отклонение ask/bid).
   * Нормализация: Z-score.

2. **Канал 1: Log Volume**
   * Формула: `log(1 + V)` (агрегированный объем уровня).
   * Нормализация: Z-score.

3. **Канал 2: Static Level Imbalance**
   * Формула: `(Vbid - Vask) / (Vbid + Vask + 1e-7)`.
   * Диапазон: `[-1, 1]`.
   * **Важно:** Z-score нормализация для этого канала не требуется.

**Порядок каналов:** [Price, Volume, Imbalance]. Порядок должен быть идентичен в коде обучения и в Rust-инференсе.

## Технические требования

* **Чередование колонок:** Обязательно использовать формат p_0, v_0, p_1, v_1.... Это упрощает итерацию по уровням в Rust и векторизацию в Python.
* **Типы данных:** В Parquet использовать float (f32) для цен и объемов. Это экономит 50% места по сравнению с f64, а точности f32 более чем достаточно для нормализованных данных в ML.
* **Метаданные:** last_update_id (поле u в Bybit) обязательно для проверки последовательности обновлений.

**Почему это важно:** Жёсткая схема предотвращает «смещение» (misalignment) данных. Если в процессе разработки мы случайно поменяем порядок колонок, LiT-модель будет получать на вход неверные цены, что приведет к ложным сигналам. Полный список в JSON позволит автоматически генерировать код валидации.
