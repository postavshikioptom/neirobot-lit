# Задача №165: Анти-адверсариальная защита (Anti-Adversarial Protection)

**Цель**: Защита бота от "токсичного" потока (Informed Trading) и манипуляций в стакане (Spoofing, Layering). Бот должен распознавать признаки Adverse Selection (отрицательного отбора), когда исполнение ордера ведет к мгновенному убытку из-за действий более информированных игроков.

---

## План реализации для Gemini AI Coder:

### 1. Изменения в [./src/config/types.rs](./src/config/types.rs)
Добавить структуру `AdversarialConfig`:
- **`vpin_buckets_count`**: `usize` (количество корзин для расчета VPIN, например, 50).
- **`vpin_volume_threshold`**: `f64` (объем одной корзины).
- **`layering_std_threshold`**: `f64` (порог стандартного отклонения ценовых шагов для детекции Layering).
- **`spoofing_min_vol_multiple`**: `f64` (во сколько раз объем уровня должен превышать средний, чтобы считаться спуфингом).

### 2. Создание модуля [./src/risk/adversarial_detector.rs](./src/risk/adversarial_detector.rs)
Реализовать структуру `AdversarialDetector` с **изоляцией per-token** (инстанцируется в `run-bot.rs` для каждого бота):

#### А. Расчет VPIN (Volume-Synchronized Probability of Informed Trading)
Реализовать инкрементальный расчет по формуле:
$$VPIN = \frac{\sum_{i=1}^{n} |V_i^{buy} - V_i^{sell}|}{n \cdot V_{bucket}}$$
- **Механизм**: Классификация объема (`buy` vs `sell`) через Tick Test (сравнение цены сделки с ценой предыдущей сделки или Mid Price).
- **Оптимизация**: Использовать `VecDeque` для хранения последних `n` корзин. Для суммирования объемов рассмотреть `std::simd` (задача [078](./docs/000-tasks_list.md)) для минимизации латентности.

#### Б. Детекция Layering (Слоистость)
- **Алгоритм**: Расчет `std_dev` (стандартного отклонения) ценовых зазоров между топ-10 уровнями стакана. 
- **Логика**: Если `std_dev(price_deltas) < layering_std_threshold`, это признак неестественно плотного и равномерного выставления ордеров (алгоритмический Layering).

#### В. Детекция Spoofing (Спуфинг)
- **Алгоритм**: Мониторинг "жизненного цикла" аномально крупных ордеров.
- **Логика**: Если уровень с объемом `> avg_vol * spoofing_min_vol_multiple` исчезает (Canceled) при приближении цены к нему без совершения сделок (`fills == 0`), выставлять флаг `SpoofingDetected`.

### 3. Интеграция в [./src/trading/execution.rs](./src/trading/execution.rs)
Внедрить защитный гейт в `can_execute`:
```rust
let is_toxic = detector.update_and_check(current_lob, last_trades);
if is_toxic {
    // Self-contained fallback: если логика смещения из 164 не готова, просто скипаем
    log::warn!("[Adversarial] Toxic flow detected, skipping signal");
    return ExecutionAction::Skip;
}
```

### 4. Оптимизация производительности
- **Zero-allocation**: Использовать `smallvec` для анализа топ-уровней стакана, чтобы избежать аллокаций в горячем цикле.
- **Incremental Updates**: Не пересчитывать весь стакан с нуля; обновлять метрики только по изменениям (`OrderBookUpdate`).

## Проверка и обоснование (спор с Grok):
1. **Почему VPIN важен?**: Простой дисбаланс стакана (Imbalance) легко подделать. VPIN основан на реальных сделках и объемах, что делает его более надежным индикатором токсичности.
2. **Изоляция**: `AdversarialDetector` должен владеть собственным состоянием (историей корзин), так как у каждого токена своя волатильность и профиль ликвидности.
3. **Layering детали**: Использование `std_dev` цен позволяет математически доказать "неестественность" структуры стакана, что точнее, чем простое визуальное сравнение.
4. **Fallback**: Если задача [164](./docs/000-tasks_list.md) (Maker-логика) не реализована, бот должен просто блокировать вход (Skip), так как торговля против токсичного потока — прямой путь к банкротству.
