# Задача 202: Анализ качества исполнения в зависимости от задержки (Execution Quality by Latency)

## 1. Цель задачи
Определить «точку деградации» стратегии: как задержка (latency) влияет на вероятность исполнения (Fill Rate) и на сколько быстро исчезает предсказательная сила сигнала (Alpha Decay).

## 2. Инструкции для Gemini по реализации

### А. Изменения в Rust-ядре (Advanced Metrics)

1.  **Типы данных и замеры ([./src/trading/order_manager.rs](./src/trading/order_manager.rs))**:
    *   Использовать **`u64`** для хранения микросекунд (`as_micros()`). Этого достаточно для интервалов до 500 лет, и это эффективнее `u128`.
    *   Разделять задержку на:
        *   `internal_lat_us`: Время обработки внутри Rust (от `Signal` до отправки запроса).
        *   `network_lat_us`: Время сетевого плеча (от отправки до получения подтверждения от Bybit).

2.  **Новый файл логов ([./src/utils/logger.rs](./src/utils/logger.rs))**:
    *   Создать **`execution_quality.csv`** в папке бота.
    *   **Критически важно**: добавить колонки `order_id` и `timestamp` (Unix MS) для возможности **JOIN** (слияния) этого файла с `trades.csv` из задачи 201.
    *   **Колонки**: `timestamp`, `order_id`, `internal_lat_us`, `network_lat_us`, `fill_rate` (объем исполнен / объем заявлен), `is_cancelled`.

3.  **Метрика Reversion (Alpha Decay)**:
    *   **НЕ использовать** задержку в 1 секунду (избегаем гонок данных и лишних таймеров).
    *   Вместо этого фиксировать `mid_price_100ms`: цену через 100мс после исполнения (минимальный безопасный порог для HFT-анализа) или сравнивать цену исполнения с `expected_price` из момента сигнала.

### Б. Изменения в Python Lab (Analytics)

1.  **Скрипт анализа**:
    *   Путь: **[./python_lab/scripts/execution_analysis.py](./python_lab/scripts/execution_analysis.py)**.
    *   **Функционал**:
        *   Загрузка `execution_quality.csv` и `trades.csv`.
        *   Мердж по `order_id`.
        *   Группировка по «бакетам» задержки (шаг 5мс или 10мс).
        *   Расчет **Fill Rate Correlation**: как вероятность «взятия» лимитки падает с ростом сетевого лага.

## 3. Аргументация и правки (По следам Grok)
*   **Спор о типах**: Согласен, `u64` для микросекунд — стандарт индустрии. Переход на `u128` избыточен.
*   **Спор о 1s Reversion**: Grok прав, 1 секунда для скальпинга — это вечность. 100мс — гораздо более релевантный показатель для оценки «токсичности» потока и качества входа.
*   **Спор о файлах**: Разделение на два CSV (`trades` и `execution`) оправдано для чистоты данных, но требует наличия `order_id` в обоих для аналитики.

## 4. Ожидаемый результат
Аналитический отчет, показывающий: *"При росте внутренней задержки выше 2000 мкс (2мс), наш Fill Rate на Bybit падает на 15%, что делает стратегию убыточной"*.
