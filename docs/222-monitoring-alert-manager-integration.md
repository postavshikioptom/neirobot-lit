# Задача 222: Интеграция менеджера алертов (Alert Manager Integration)

## 1. Цель задачи
Реализовать компонент `AlertManager` для интеллектуальной фильтрации и отправки уведомлений. Система должна поддерживать уровни критичности, маршрутизацию (Routing), дедупликацию и гарантированную доставку критических сообщений через Telegram API с учетом лимитов биржи.

## 2. Инструкции для Gemini по реализации

### А. Ядро системы уведомлений (Rust)

1.  **Маршрутизация по уровням ([./src/monitoring/alert_manager.rs](./src/monitoring/alert_manager.rs))**:
    *   **Info**: Только запись в стандартный `bot.log`.
    *   **Warning**: Запись в `bot.log` + запись в `security_audit.csv` (задача 217).
    *   **Critical**: Логирование + немедленная отправка в Telegram.

2.  **Защита от шторма (Deduplication)**:
    *   Использовать `DashMap` для хранения хешей последних сообщений (`msg_hash + source`).
    *   Реализовать **TTL (Time-To-Live)**: не отправлять дубликат сообщения в течение 5–10 минут.

3.  **Telegram-транспорт и устойчивость**:
    *   **Retry Queue**: Создать ограниченную очередь (bounded queue) для повторных попыток при сбоях сети (3 попытки с экспоненциальным бэкаффом).
    *   **Rate Limit (429)**: При получении ошибки `429 Too Many Requests` от Telegram, приостановить отправку на время, указанное в ответе (`retry_after`).
    *   **Зависимости**: `reqwest = { version = "0.11", features = ["json"] }`, `dashmap = "5.5"`.

### Б. Конфигурация и Иерархия

1.  **Конфигурация ([./src/config/types.rs](./src/config/types.rs))**:
    *   `GlobalConfig`: Общие `telegram_token` и `default_chat_id`.
    *   `BotConfig`: Опциональный `override_chat_id` (позволяет разным ботам слать алерты в разные каналы).
    *   Обязательная поддержка префикса `ENC:` для токена (задача 216).

2.  **Интеграция с Аудитом**:
    *   Все критические алерты должны проходить через `AuditLogger` (задача 217) для включения в защищенную цепочку хешей.

### В. Тестирование и Валидация

1.  **CLI Триггер**:
    *   Добавить в `run-bot.rs` поддержку команды `--test-alert "message"`, которая инициирует отправку тестового сообщения через всю цепочку (SOR -> AlertManager -> Telegram).

## 3. Критика и аргументация (По правкам Grok)
*   **Спор об иерархии**: Полностью согласен. В условиях «фермы» ботов (Phase 30) слать всё в один канал — это хаос. Поддержка `override_chat_id` в `BotConfig` позволяет группировать уведомления по стратегиям или рискам.
*   **Спор о дедупликации**: Использование `DashMap` для асинхронного кеширования «виденных» алертов необходимо, чтобы не заспамить трейдера при циклической ошибке WebSocket.
*   **Спор о надежности**: Очередь повторных попыток критична. Если в момент падения бота пропал интернет, алерт о смерти (Last Gasp) не должен просто исчезнуть — он должен быть отправлен сразу после восстановления связи.

## 4. Ожидаемый результат
При возникновении критического события (например, `Critical` из задачи 220) бот пишет захешированную запись в аудит-лог и отправляет структурированное сообщение в Telegram, учитывая лимиты API и предотвращая повторы.
