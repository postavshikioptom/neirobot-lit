# Задача 204: Анализ влияния сделок на Mid-Price (Trade Impact on Mid-Price)

## 1. Цель задачи
Измерить «цену нашего присутствия»: на сколько базисных пунктов (bps) изменяется `mid_price` в процессе и после исполнения нашего ордера. Это критично для расчета **Capacity** (максимальной емкости) стратегии.

## 2. Инструкции для Gemini по реализации

### А. Изменения в Rust-ядре (Partial Fills & Logging)

1.  **Логика захвата цен ([./src/trading/order_manager.rs](./src/trading/order_manager.rs))**:
    *   В момент **создания** ордера фиксировать `mid_price_before`.
    *   **ВАЖНО**: При получении каждого события `Fill` (учитывая частичные исполнения), фиксировать текущий `mid_price` стакана.
    *   **НЕ агрегировать** данные в Rust — передавать сырые данные в логи для максимальной точности в Python.

2.  **Файл логов ([./src/utils/logger.rs](./src/utils/logger.rs))**:
    *   Использовать **`market_impact.csv`**.
    *   **Колонки**: `timestamp`, `order_id`, `fill_id`, `side`, `fill_size`, `mid_before` (цена в момент постановки), `mid_at_fill` (цена в момент конкретного частичного исполнения).
    *   **Конфиг**: Добавить `enable_impact_logging: bool` в `BotConfig`.

### Б. Изменения в Python Lab (Analytics)

1.  **Скрипт анализа**:
    *   Путь: **[./python_lab/scripts/market_impact_analysis.py](./python_lab/scripts/market_impact_analysis.py)**.
    *   **Методология**:
        *   **Weighted Average Impact**: Расчет средневзвешенного импакта на один `order_id` (сумма `fill_size * (mid_at_fill - mid_before)` / `total_size`).
        *   **Normalization**: Выполнить **JOIN** с `order_context.csv` ([./docs/203-analysis-fill-rate-distribution-study.md](./docs/203-analysis-fill-rate-distribution-study.md)) по `order_id`, чтобы получить `level_total_vol`.
        *   Построить кривую: `impact_bps` как функция от `order_size / level_total_vol`.

## 3. Спорные моменты и аргументация (Против Grok)

*   **Спор о частичных исполнениях**: Согласен с Grok. Игнорировать Partial Fills нельзя — на Bybit крупный ордер может дробиться на 20-30 мелких сделок. Логирование каждого `fill_id` дает нам понимание «динамики проедания стакана».
*   **Спор об агрегации**: **Не согласен с Grok** в части агрегации в Rust. Любая агрегация в Hot Path — это лишние вычисления и риск потери гранулярности. Намного надежнее писать в CSV каждую частичную сделку, а Python (через Polars) склеит их за миллисекунды.
*   **Спор о 100мс**: Согласен, «перманентный импакт» лучше считать в Python, соединяя данные с `mid_100ms` из задачи 202.

## 4. Ожидаемый результат
Аналитическая модель: *"Сделка размером 5% от объема уровня (Top level) вызывает мгновенное смещение цены на 0.8 bps, которое восстанавливается на 50% через 100мс"*.
