# Задача №153: Внедрение Purged K-Fold кросс-валидации (по де Прадо)

Согласно [./docs/000-architecture.md](./docs/000-architecture.md), мы работаем с высокочастотными данными стакана (LOB). Обычная кросс-валидация здесь "убивает" модель из-за утечки данных. Мы внедрим метод **Purged K-Fold** с раздельной логикой очистки (Purge) и эмбарго (Embargo).

## План реализации для Gemini AI Coder:

### 1. Реализация Splitting-логики в [./python_lab/src/utils.py](./python_lab/src/utils.py)
Создать класс `PurgedKFold`, совместимый с интерфейсом `sklearn.model_selection`.
- **Purging (До валидации)**: Удаление из обучения сэмплов, чьи метки перекрываются с началом валидационного блока.
- **Embargo (После валидации)**: Удаление сэмплов сразу после валидационного блока, так как автокорреляция признаков в LOB затухает не мгновенно.
- **Параметры**: `purge_buffer_events` и `embargo_buffer_events` (использовать количество событий вместо секунд для устойчивости к пропускам в данных/гэпам).
- **Интерфейс**: Метод `.split(X, y, timestamps)` должен быть генератором и возвращать `(train_indices, val_indices)`.

### 2. Обновление [./python_lab/src/dataset.py](./python_lab/src/dataset.py)
- **Сортировка**: Убедиться, что при загрузке данных из Parquet (задача 021) выполняется строгая сортировка по `timestamp`.
- **Subsetting**: Использовать стандартный `torch.utils.data.Subset` для создания фолдов.
- **Gaps Handling**: Если временные метки имеют большие разрывы (низкая ликвидность ночью), логика очистки должна автоматически переключаться на индексную дистанцию (`events count`).

### 3. Интеграция в [./python_lab/scripts/train.py](./python_lab/scripts/train.py)
- **Флаг `--mode cv`**:
    1. Инициализировать `PurgedKFold(n_splits=5)`.
    2. В цикле по фолдам:
        - **Важно**: Выполнять полную инициализацию модели (`fresh weights`) в начале каждого фолда.
        - Использовать `EarlyStopping` независимо для каждого фолда.
    3. Агрегировать **MCC** (задача 051) и сохранять `mean` ± `std`.
- **Вывод**: Печатать в лог процент удаленных данных ("leakage prevention overhead").

### 4. Оптимизация через Optuna (задача 030)
- **Pruning**: Для ускорения CV-поиска внедрить `optuna.pruners.MedianPruner()`. Если средний MCC по первым двум фолдам значительно хуже лучших результатов, прекращать обучение текущего триала.
- **Objective**: Возвращать среднее значение MCC по всем валидационным фолдам.

### 5. Метрики и Валидация
- Сравнивать результаты на **Purged CV** и на **Holdout** сете. Если разница MCC > 15%, сигнализировать о нестабильности признаков (Data Drift).

## Аргументация (Спор с Grok):
- **Согласен**: Разделение параметров `purge` и `embargo` — это стандарт де Прадо, который мы обязаны соблюдать.
- **Согласен**: Использование `torch.utils.data.Subset` — самый чистый способ работы с фолдами в PyTorch, избегаем лишних кастомных оберток.
- **Согласен**: Переход на события (`events count`) вместо секунд — это критично для LOB, где плотность данных меняется в 100 раз в зависимости от времени суток.
