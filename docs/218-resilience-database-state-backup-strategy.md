# Задача 218: Стратегия резервного копирования состояния (State Backup Strategy)

## 1. Цель задачи
Реализовать систему персистентного хранения внутреннего состояния торгового ядра. Бот должен атомарно сохранять позицию, PnL и активные ордера, защищая данные от одновременного доступа (Locking) и обеспечивая возможность отката к предыдущим копиям (Rotation).

## 2. Инструкции для Gemini по реализации

### А. Изменения в Rust-ядре (Reliability & Safety)

1.  **Зависимости ([./Cargo.toml](./Cargo.toml))**:
    *   `serde_json = "1.0"` (JSON для прозрачности).
    *   `tempfile = "3.10"` (Атомарная запись через временный файл).
    *   `fs2 = "0.4"` (Advisory file locking).
    *   `sha2 = "0.10"` (Проверка целостности состояния).

2.  **Структура BotState ([./src/trading/state_persistence.rs](./src/trading/state_persistence.rs))**:
    ```rust
    struct BotState {
        version: u32,             // Версия схемы для миграций
        timestamp: u64,           // Время сохранения
        data: BotStateData,       // PnL, Position, OrderIds
        checksum: String,         // SHA256 от поля data
    }
    ```

3.  **Атомарная запись и Ротация**:
    *   **Механизм**:
        1.  Перед записью нового состояния переместить текущий `state.json` в `state.json.bak.1`.
        2.  Выполнить ротацию старых бэкапов до `max_state_backups` (например, `.1` -> `.2`).
        3.  Использовать `tempfile` для записи нового состояния, вызвать `fsync()` и выполнить `rename` в `state.json`.
    *   **Блокировка**: Использовать `fs2::FileExt::lock_exclusive` на файл состояния, чтобы предотвратить запуск двух копий бота на одном токене.

4.  **Логика восстановления (Recovery)**:
    *   При загрузке проверять `checksum`. Если данные повреждены — пытаться загрузить последний валидный бэкап.
    *   Если все копии повреждены — логировать **Critical Error**, инициализировать пустое состояние и принудительно синхронизироваться с биржей через REST (задача 066).

## 3. Критика и аргументация (По правкам Grok)
*   **Спор о блокировке (Locking)**: Согласен с Grok. При использовании систем автоматического перезапуска (Watchdog) возможна ситуация «гонки», когда новый процесс стартует до того, как старый полностью освободил ресурсы. `fs2` — стандартное решение этой проблемы.
*   **Спор о ротации**: Ротация бэкапов необходима. Если ошибка логики запишет некорректное состояние в файл, у нас должна быть возможность откатиться на шаг назад, а не просто потерять всё.
*   **Спор о чексумах**: SHA256 в теле JSON гарантирует, что мы не загрузим «битый» файл, который мог возникнуть при сбое файловой системы или диска.

## 4. Ожидаемый результат
Бот имеет «память», защищенную от сбоев питания и конфликтов процессов. Файл `state.json` всегда целостен, а в случае катастрофической ошибки доступны последние рабочие копии.
