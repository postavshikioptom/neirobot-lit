# Задача №166: Частичная фиксация прибыли (Partial Profit Taking)

**Цель**: Снижение рыночного риска и стабилизация кривой доходности за счет поэтапного закрытия позиции. Реализация логики "выхода частями" при достижении заданных уровней профита, выраженных в базисных пунктах (bps).

---

## План реализации для Gemini AI Coder:

### 1. Изменения в [./src/config/types.rs](./src/config/types.rs)
Добавить конфигурацию в `StrategyConfig` (загружается per-bot через `BotConfig`):
- **`tp_stages`**: `Vec<TpStage>` (список уровней фиксации).
- **`TpStage`**:
    - `threshold_bps`: `u32` (дистанция от цены входа).
    - `close_pct`: `f64` (процент от **initial_size** для закрытия, 0.0 - 1.0).
- **`tp_close_all_on_min_qty`**: `bool` (если остаток меньше `min_qty`, закрывать ли позицию полностью).

### 2. Состояние в [./src/trading/position_manager.rs](./src/trading/position_manager.rs)
Обновить структуру `Position` для отслеживания прогресса:
- **`completed_tp_stages`**: `HashSet<usize>` (индексы пройденных этапов).
- **`initial_size`**: `f64` (размер позиции в момент открытия для расчета долей закрытия).
- **`side`**: `Side` (`Buy` для Long, `Sell` для Short) — использовать для направления расчета профита.

### 3. Логика в [./src/trading/execution.rs](./src/trading/execution.rs)
Реализовать проверку условий в хуке `on_ob_update` (вместо `run-bot.rs` для соблюдения чистоты слоев):
- **Расчет отклонения (Side-aware)**:
  ```rust
  let deviation_bps = if position.side == Side::Buy {
      (mid_price - entry) / entry * 10000.0
  } else {
      (entry - mid_price) / entry * 10000.0
  };
  ```
- **Итерация по стадиям**: Если `deviation_bps >= stage.threshold_bps` и стадия еще не выполнена — инициировать сигнал `ExecutionAction::PartialClose`.

### 4. Исполнение в [./src/trading/order_manager.rs](./src/trading/order_manager.rs)
- **Проверка лимитов (Bybit Specifics)**:
    - Получить `min_qty` для текущего символа через `exchange_config` (задача [003](./docs/000-tasks_list.md)).
    - Если `size_to_close < min_qty`:
        - Если `tp_close_all_on_min_qty == true`, закрыть всю позицию.
        - Иначе пропустить стадию (лог `warn`).
- **Maker-исполнение**: Использовать `maker_offset` из задачи [164](./docs/000-tasks_list.md) для минимизации комиссий при фиксации профита.

### 5. Тестирование и валидация
- **Unit-тесты**: Создать `tests/position_manager_pnl_consistency.rs`.
- **Сценарий**: Имитация открытия позиции -> Частичное закрытие 50% -> Полное закрытие. Проверка, что `realized_pnl` корректно учитывает обе сделки и комиссии (`fee`).
- **Интеграция**: Проверить в `run-bot.rs`, что цепочка `WS -> OrderBook -> Execution -> OrderManager` корректно обрабатывает уменьшение размера позиции без её полного удаления из `PositionManager`.

## Аргументация (ответы на замечания Grok):
1. **Направление (Side)**: План теперь явно учитывает `Side` позиции. Профит для Short считается от падения цены, для Long — от роста.
2. **Локация логики**: Логика перенесена в `execution.rs`, что соответствует архитектуре: `run-bot` только доставляет данные, а `execution` принимает бизнес-решения.
3. **Минимальный лот**: Проблема `min_qty` решена через интеграцию с `exchange_config` и REST-информацией о тикерах, чтобы избежать `OrderLessThenMinQty` ошибок от Bybit.
4. **PnL Consistency**: Добавление тестов на консистентность PnL критично, так как частичные закрытия часто приводят к ошибкам округления или неверному учету средней цены входа.

**Gemini, твоя задача — обеспечить хирургическую точность при фиксации прибыли. Каждый "базисный пункт" должен быть отработан согласно конфигу бота.**
