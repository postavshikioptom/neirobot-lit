# Задача 225: Живой профилировщик системных ресурсов (System Resource Profiler Live)

## 1. Цель задачи
Реализовать систему непрерывного мониторинга технического состояния бота (CPU, RAM, Disk/Network I/O). Это необходимо для обнаружения утечек памяти, перегрузки процессора и их влияния на задержки исполнения, а также для автоматического снижения рисков при дефиците ресурсов.

## 2. Инструкции для Gemini по реализации

### А. Сбор метрик в Rust (Backend)

1.  **Зависимости ([./Cargo.toml](./Cargo.toml))**:
    *   `sysinfo = "0.30"` (сбор системных данных).

2.  **Модуль профилирования ([./src/monitoring/resource_profiler.rs](./src/monitoring/resource_profiler.rs))**:
    *   **Разделение потоков**: НЕ использовать `EquityUpdate`. Создать отдельную структуру и канал трансляции `SystemMetricsUpdate`.
    *   **Сглаживание (EMA)**: Применять EMA к `cpu_usage` и `memory_rss`, чтобы избежать ложных алертов на системных всплесках (GC, OS scheduling).
    *   **Расширенные метрики**: Добавить мониторинг Disk I/O (bytes read/write) и Network I/O для детекции сетевых заторов.

3.  **Интеграция с состоянием здоровья ([./src/trading/risk_manager.rs](./src/trading/risk_manager.rs))**:
    *   **Связь с 220**: Если EMA CPU > `cpu_max_pct`, принудительно переводить систему в состояние `Degraded` (так как рост нагрузки ведет к росту задержек инференса).
    *   **Leak Detection**: Реализовать в Rust простейший детектор «наклона» (slope) для RAM: если EMA памяти растет на протяжении N циклов — слать `Warning Alert` (задача 222).

### Б. Конфигурация и Аналитика

1.  **Конфигурация ([./src/config/types.rs](./src/config/types.rs))**:
    *   Добавить в `BotConfig` секцию `resource_thresholds`:
        ```rust
        cpu_max_pct: f32,
        mem_growth_kb_min: u64,
        sample_interval_sec: u64,
        ```

2.  **Скрипт анализа ([./python_lab/scripts/resource_analyzer.py](./python_lab/scripts/resource_analyzer.py))**:
    *   Корреляция между системной нагрузкой и `internal_latency_us` из логов исполнения.

## 3. Критика и аргументация (По правкам Grok)
*   **Спор о разделении данных**: Полностью согласен. Смешивание PnL и загрузки CPU в одной структуре — плохая практика. Технический мониторинг должен идти по своему каналу, чтобы не «засорять» финансовый дашборд.
*   **Спор об EMA**: Использование EMA критично. Без сглаживания любой фоновый процесс ОС (например, `updatedb` или лог-ротация) вызовет ложное срабатывание риск-гейта.
*   **Спор об I/O**: Мониторинг сетевого и дискового ввода-вывода необходим, так как задержки записи логов или перегрузка сетевой карты могут стать «невидимой» причиной проскальзывания.

## 4. Ожидаемый результат
Бот транслирует свои технические параметры через выделенный WebSocket. При превышении нагрузки на CPU он автоматически снижает объем торгов (через `SystemHealthState`), защищая стратегию от непредсказуемых задержек.
