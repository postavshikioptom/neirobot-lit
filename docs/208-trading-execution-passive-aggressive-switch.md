# Задача 208: Динамическое переключение Passive -> Aggressive (Safe Chasing)

## 1. Цель задачи
Реализовать безопасный механизм «догона» цены: если пассивный лимитный ордер не исполняется, бот должен переключиться в агрессивный режим. Переключение должно быть защищено от гонок данных и модулироваться «срочностью» (urgency) сигнала.

## 2. Инструкции для Gemini по реализации

### А. Изменения в Rust-ядре (Safe Execution & Modulation)

1.  **Безопасный триггер переключения ([./src/trading/order_manager.rs](./src/trading/order_manager.rs))**:
    *   **КРИТИЧЕСКИ ВАЖНО**: Запрещено отправлять агрессивный ордер до получения подтверждения отмены лимитного.
    *   Реализовать `async fn handle_switch_trigger`:
        1.  Отправить запрос на отмену (`cancel_order`).
        2.  Дождаться ответа: если `Success` или `OrderNotFound` (значит, уже исполнился или удален) — проверить `remaining_size`.
        3.  Если `remaining_size > 0` — отправить агрессивный ордер (Market или Cross-Limit).

2.  **Модуляция по Urgency ([./src/trading/execution.rs](./src/trading/execution.rs))**:
    *   Использовать `urgency` (0.0 - 1.0) из задачи 206 для корректировки порогов:
        *   `effective_timeout = base_timeout / (1.0 + urgency)`.
        *   `effective_distance = base_distance / (1.0 + urgency)`.
    *   Чем сильнее сигнал, тем быстрее бот переходит к агрессии.

3.  **Защита от циклов (Loop Protection)**:
    *   Добавить в состояние ордера `switch_count: u8`.
    *   Лимит: **максимум 1 переключение на один сигнал**. Это предотвратит бесконечный цикл «отмена - погоня - отмена» при экстремальной волатильности.

4.  **Конфигурация ([./src/config/types.rs](./src/config/types.rs))**:
    *   Добавить в `SorConfig`:
        ```rust
        switch_base_timeout_ms: u64,
        switch_base_distance_bps: u32,
        max_switches_per_signal: u8, // Default 1
        ```

### Б. Изменения в Python Lab (Analytics)

1.  **Скрипт оптимизации**:
    *   Путь: **[./python_lab/scripts/switch_optimization.py](./python_lab/scripts/switch_optimization.py)**.
    *   **Функционал**: Анализ «упущенной выгоды» (Opportunity Cost). Поиск баланса между экономией на Maker-комиссии и потерей Alpha из-за неисполнения.

## 3. Критика и аргументация (По правкам Grok)
*   **Спор об атомарности**: Полностью согласен. Bybit (и другие биржи) не гарантируют атомарность отмены и замены. Предложенный Grok паттерн `cancel -> confirm -> send` — единственный способ избежать «двойной позиции», которая может убить депозит.
*   **Спор об Urgency**: Интеграция с 206-й задачей делает систему целостной. Бот ведет себя по-разному для «слабых» и «сильных» предсказаний модели.
*   **Спор о циклах**: Ограничение `max_switch = 1` крайне важно. В HFT-среде без этого лимита бот может «зациклиться», генерируя тысячи ордеров в секунду на одном тике, что приведет к бану API-ключа.

## 4. Ожидаемый результат
Бот перестает «стоять» в стакане, когда цена уже ушла. В логах `execution_quality.csv` появляется статус `final_type: Taker_After_Passive`, а `switch_latency_ms` показывает время от триггера до подтверждения отмены.
