# Задача №192: Оптимизация производительности: Zero-Copy парсинг JSON

[./docs/192-performance-zero-copy-json-parsing.md](./docs/192-performance-zero-copy-json-parsing.md)

## План реализации

1.  **Обновление зависимостей**:
    - Добавить `serde_with = "3.11"` и `fast-float = "0.2"` в `Cargo.toml`.

2.  **Изменения в [./src/data/types.rs](./src/data/types.rs)**:
    - Добавить лайфтаймы к основным структурам данных: `OrderBookUpdate<'a>`, `Ticker<'a>`, `PublicTrade<'a>`.
    - Заменить поля `String` на `&'a str`, пометив их атрибутом `#[serde(borrow)]`. Это позволит `serde_json` заимствовать данные напрямую из исходного буфера сообщения.
    - Использовать макрос `#[serde_as]` и атрибут `#[serde_as(as = "DisplayFromStr")]` для полей `f64` (цена, объем), которые в API Bybit передаются как строки. Это исключит создание промежуточных объектов `String` при парсинге чисел.

3.  **Изменения в [./src/data/websocket.rs](./src/data/websocket.rs)**:
    - Обновить обработчик `on_message`, чтобы он десериализовал входящий JSON-буфер в структуры с лайфтаймами.
    - Исключить любые вызовы `.to_string()` или `.clone()` для строковых данных, приходящих от биржи, передавая ссылки в стакан и другие компоненты.

4.  **Оптимизация парсинга чисел**:
    - В кастомных десериализаторах (если потребуется для максимальной скорости) заменить стандартный `f64::from_str` на `fast_float::parse`, чтобы ускорить обработку числовых полей в тяжелых пакетах стакана.

## Ожидаемый результат
- Снижение нагрузки на аллокатор памяти (Heap allocations) за счет переиспользования исходного буфера сообщения.
- Уменьшение задержки десериализации (P99 latency) при обработке плотных потоков обновлений стакана.
- Отсутствие лишних аллокаций `String` для полей `symbol`, `topic` и числовых значений.
