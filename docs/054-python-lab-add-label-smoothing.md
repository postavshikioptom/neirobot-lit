Задача 054-python-lab-add-label-smoothing.md
Цель: Внедрить механизм Label Smoothing для снижения излишней уверенности модели и улучшения калибровки вероятностей, интегрировав его в систему подбора гиперпараметров.

Инструкции для Gemini:
1. Изменения в ./python_lab/scripts/train.py
Параметризация:
Добавить аргумент CLI --label_smoothing (по умолчанию 0.1).
Интеграция с Optuna (Задача 030): Добавить label_smoothing в пространство поиска гиперпараметров (диапазон 0.0 – 0.2).
Инициализация Loss:
Использовать nn.CrossEntropyLoss(weight=class_weights, label_smoothing=args.label_smoothing).
Важно: Добавить проверку: если в будущем будет включен Focal Loss (Задача 057), label_smoothing в CrossEntropyLoss должен быть отключен, так как эти методы являются альтернативами.
Логирование: Выводить финальное значение сглаживания, выбранное Optuna или переданное через CLI.
2. Изменения в ./python_lab/requirements.txt
Установить жесткое требование: torch>=2.0.0. Это гарантирует корректную работу сглаживания совместно с весами классов и стабильный экспорт в ONNX.
3. Изменения в ./docs/000-tasks_list.md
Добавить примечание к задаче 057: "Focal Loss и Label Smoothing — альтернативные методы. Рекомендуется проводить ablation studies перед их одновременным использованием".
Аргументация изменений:
Torch 2.0+: Решает проблемы совместимости label_smoothing с Automatic Mixed Precision (AMP) и корректно обрабатывает weight при расчете сглаженного таргета.
Optuna Integration: В крипто-LOB уровень шума меняется от токена к токену. Фиксированное значение 0.1 может быть избыточным для стабильных пар и недостаточным для высоковолатильных "щиткоинов".
Архитектурная гибкость: Мы явно разделяем методы борьбы с дисбалансом (Weights/Focal) и борьбы с шумом (Smoothing), предотвращая их непредсказуемую интерференцию.
Критическое требование: Убедиться, что при расчете валидационных метрик (Accuracy/MCC) используются исходные "жесткие" метки, а не сглаженные, чтобы оценка оставалась объективной.
