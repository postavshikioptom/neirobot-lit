# Задача 220: Режим «грациозной деградации» (Graceful Degradation Mode)

## 1. Цель задачи
Реализовать систему автоматического управления состояниями риска бота. Бот должен динамически переходить в защищенные режимы (Degraded, Emergency, Halted) при обнаружении технических сбоев, обеспечивая автоматическое восстановление при стабилизации метрик.

## 2. Инструкции для Gemini по реализации

### А. Состояния и Метрики ([./src/trading/mod.rs](./src/trading/mod.rs))

1.  **Определение состояний**:
    ```rust
    pub enum SystemHealthState {
        Healthy,    // Полная работа
        Degraded,   // Снижение объема (50%), задержки инференса
        Emergency,  // Только закрытие (Reduce-Only), критические лаги или ошибки API
        Halted,     // Полная остановка, крах ONNX или потеря связи
    }
    ```

2.  **Скользящие метрики (Rolling Stats)**:
    *   Реализовать в `RiskManager` структуру для расчета экспоненциального скользящего среднего (**EMA**) для:
        *   `inference_latency_ema`: Среднее время инференса (за последние 100 запросов).
        *   `api_error_rate_ema`: Процент ошибок за последние 5 минут (decay-based).

### Б. Триггеры и Гистерезис ([./src/trading/risk_manager.rs](./src/trading/risk_manager.rs))

1.  **Триггеры деградации**:
    *   **ONNX-специфичные**: Ошибки `onnxruntime` при инференсе или сбой загрузки модели немедленно переводят бота в `Halted`.
    *   **Data Staleness**: Если `timestamp` последнего снимка стакана старше 1000мс → `Emergency`.
    *   **Performance**: EMA задержки инференса > `max_inference_ms` → `Degraded`.

2.  **Защита от «флаппинга» (Hysteresis)**:
    *   Переход «вниз» (в сторону риска) происходит мгновенно.
    *   Переход «вверх» (восстановление в `Healthy`) возможен только если метрики в норме в течение **N секунд** (например, 60с), заданных в `BotConfig`.

3.  **Интеграция с Risk Gates**:
    *   В режиме `Emergency` принудительно переопределять `max_position_size` текущим размером позиции (`current_pos`), блокируя любое увеличение экспозиции.

### В. Конфигурация и Аудит

1.  **Конфигурация ([./src/config/types.rs](./src/config/types.rs))**:
    *   Расширить `BotConfig` секцией `degradation`: `recovery_hysteresis_sec`, `max_inference_ms`, `max_error_rate`.
2.  **Аудит ([./src/utils/audit.rs](./src/utils/audit.rs))**:
    *   Логировать каждую смену состояния через `AuditLogger` (из задачи 217).

## 3. Критика и аргументация (По правкам Grok)
*   **Спор о файлах**: Согласен с Grok. Создавать `types.rs` для одного Enum избыточно. Размещение в `trading/mod.rs` логично, так как это влияет на всё поведение торгового ядра.
*   **Спор об ONNX**: Добавление явной проверки на ошибки инференса — критическое улучшение. Если нейросеть начинает выдавать ошибки или «мусор», бот обязан немедленно прекратить торговлю.
*   **Спор о гистерезисе**: Без таймера восстановления бот будет «метаться» между состояниями при пограничных значениях задержки (например, 19мс и 21мс), генерируя лишние записи в логах и хаотично меняя объемы ордеров.
*   **Спор об интеграции**: Использование состояний для временного переопределения лимитов `RiskManager` (Override) эффективнее, чем написание дублирующей логики проверок.

## 4. Ожидаемый результат
Бот самостоятельно «сжимается» при плохой связи или тяжелых вычислениях и «расправляется» только после стабильного периода нормальной работы. Все переходы подтверждены цепочкой хешей в аудит-логе.

# Инфо для пользователя, ответ на вопрос, не инструкция для Gemini: 
Да, EMA (Exponential Moving Average) **используют** даже в микроскалпинге и HFT, включая боты с коротким горизонтом прогноза вроде вашего LiT (10–30 секунд по LOB). Но применяют его не так, как в классической внутридневной торговле (где EMA — это основной индикатор для трендов/кроссоверов на минутах-часах). В HFT/микроскалпинге EMA чаще идет на **сглаживание метрик системы** (latency, error rate, inference time, staleness), чтобы избежать ложных срабатываний kill-switch или degradation modes на одиночных спайках.

### Как рассчитывается EMA для реал-тайм метрик
Формула стандартная и не меняется даже в 2026 году:

`EMA_t = α × current_value + (1 - α) × EMA_{t-1}`

- α (smoothing factor) = 2 / (N + 1), где N — период (например, 10–50 последних измерений для latency).
- Для первого значения берут simple average или просто current.
- Это дает больше веса свежим данным, быстро реагируя на изменения, но сглаживая шум (лучше SMA).

В реал-тайм (микроданные) α делают высоким (N маленький, 5–20), чтобы EMA была чувствительной, но не дергалась на каждый тик.

### Используют ли конкуренты EMA для таких задач
Прямых публичных примеров от топ-проп фирм (Jane Street, Citadel, Jump Trading) на 2025–2026 нет — они не раскрывают internals latency monitoring. Поиск по ним дал только общие новости о revenue/hiring, ничего про EMA в kill-switch.

В crypto HFT и open-source/коммерческих ботах (Bybit-oriented, scalping на секундах):
- EMA чаще для **price/volume filtering** (short-period EMA5–21 для micro-trends, как в 2025–2026 paper "An efficient hybrid approach for forecasting real-time stock market" и IEEE crypto EMA bot).
- Для **system metrics** (latency/error rate smoothing) — да, best practice, но indirect:
  - В low-latency платформах (AWS 2025 post, B2Broker 2026) — smoothing gauges (EMA-like) для jitter detection.
  - В adaptive bots (Medium 2026 low-latency crypto HFT design) — EMA для inference/volatility metrics перед threshold.
  - Prometheus/Datadog-style monitoring в HFT (common в 2026) — EMA gauges для latency percentiles anti-spike.
  - Open bots (freqtrade extensions, Hummingbot 2025+) — EMA для adaptive risk sizing на latency spikes.

В вашем случае (LiT на LOB, 10s forecast) EMA для latency/error_rate — полностью оправдано: спайк в 1–2ms не должен сразу degrade, но sustained рост — да. Это стандартный способ избежать flapping в graceful degradation (как в QuantConnect/elite HFT setups).
