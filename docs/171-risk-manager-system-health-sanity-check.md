# **Задача №171: Проверка целостности и здоровья системы (System Health Sanity Check)**

**Цель**: Создание системы самодиагностики внутри `RiskManager` для обеспечения технической безопасности торгов. Бот должен непрерывно проверять целостность стакана (OrderBook), потребление ресурсов и задержки пайплайна, переходя в защитный режим при обнаружении аномалий.


### **2. Изменения в [./src/config/types.rs](./src/config/types.rs)**

- **`health_check_interval_s`**: `u64` (интервал проверки ресурсов, по умолчанию 10с).

### **3. Новый модуль [./src/risk/health_monitor.rs](./src/risk/health_monitor.rs)**
Реализовать структуру `HealthMonitor`, инстанцируемую в [./src/run-bot.rs](./src/run-bot.rs):

#### **А. Контроль целостности стакана (OrderBook Integrity)**
- **Метод `check_u(new_u: u64) -> bool`**: 
    - Проверять последовательность `u` (update ID) из WebSocket Bybit (задачи [018](./docs/000-tasks_list.md), [019](./docs/000-tasks_list.md)).
    - Если `new_u != last_u + 1` (обнаружен пропуск), возвращать `true` (Corrupted).
    - **Действие**: При `Corrupted` инициировать сброс и запрос нового Snapshot через `rest-client` (задача [061](./docs/000-tasks_list.md)).

#### **Б. Мониторинг задержек (Latency Tracking)**
- **Метод `update_latency(elapsed_ms: f64)`**: 
    - Использовать `VecDeque<f64>` емкостью 60 элементов для хранения задержек за последнюю минуту.
    - Замерять полный путь: от получения WS сообщения (`receive_ts`) до момента готовности ордера.
- **Метод `is_latency_ok() -> bool`**: Сравнивать `avg()` из окна с `max_avg_latency_ms`.

#### **В. Мониторинг ресурсов (Memory RSS)**
- **Использование `sysinfo`**:
  ```rust
  let mut sys = System::new_with_specifics(RefreshKind::new().with_memory());
  let pid = sysinfo::get_current_pid().unwrap();
  let rss_mb = sys.process(pid).unwrap().memory() / 1024 / 1024;
  ```

## **Аргументация и проверка (ответы на замечания Grok):**
1. **OrderBook Sequential `u`**: Простого наличия чексуммы (задача [049](./docs/000-tasks_list.md)) недостаточно. Проверка `u == last_u + 1` — это самый быстрый способ детекции сетевых разрывов до того, как они исказят расчеты модели.
2. **Resource Management**: Использование `sysinfo` версии `0.32` с `RefreshKind` позволяет минимизировать нагрузку на CPU при мониторинге ресурсов.
3. **Pipeline Latency**: Мы отслеживаем не просто "время инференса", а общее время жизни события. Если среднее за минуту (`VecDeque` на 60 точек) превышает порог — система считается деградировавшей.
4. **Bybit Resync**: При разрыве последовательности `u` бот должен не просто упасть, а попытаться восстановиться, запросив актуальный Snapshot через REST API (`/v5/market/orderbook`), что критично для 24/7 работы.
