# **Задача №185: Система контроля версий ML-моделей (Model Version Control System)**

**Цель**: Обеспечение строгой связи между артефактами обучения в `python_lab` и инференсом в Rust. Реализация системы «паспортизации» моделей, гарантирующей, что торговое ядро использует правильные веса, актуальные параметры нормализации и верифицирует целостность файлов перед запуском.

---

## **План реализации для Gemini AI Coder:**

### **1. Реестр и метаданные ([./bots/SYMBOL/model/](./bots/SYMBOL/model/))**
Реализовать локальный учет моделей для каждого бота (изоляция **per-bot**):
- **`registry.json`**: Файл-реестр со списком всех загруженных версий.
    - **Поля**: `version_tag`, `onnx_hash`, `mcc_score`, `created_at`, `file_path`.
- **`metadata.json`**: Активный «паспорт» текущей модели.
    - **Поля**: `onnx_hash` (SHA-256), `version`, `normalization`: `{ "mean": [...], "std": [...] }` (из задачи [024](./docs/000-tasks_list.md)).

### **2. Валидация в Rust ([./src/ml/onnx.rs](./src/ml/onnx.rs))**
Доработать инициализацию `InferenceEngine`:
- **Загрузка**: Использовать `serde_json` для парсинга `metadata.json`.
- **Проверка целостности**: 
    - Вычислить `SHA-256` файла `model.onnx` с помощью библиотеки `sha2`.
    - Сравнить с `onnx_hash` из метаданных. Если не совпадает — `panic!` или возврат `CriticalError`.
- **Логирование**: Выводить в лог ID и MCC модели для аудита (связь с [184](./docs/000-tasks_list.md)).

### **3. Динамическая нормализация ([./src/ml/tensor.rs](./src/ml/tensor.rs))**
Обновить логику подготовки данных (задача [034](./docs/000-tasks_list.md)):
- Вместо жестко заданных констант `mean/std`, использовать значения, загруженные из `metadata.json`.
- **Важно**: Это исключает ошибки, когда модель v2 пытается работать на параметрах нормализации от v1.

### **4. Управление в [./deploy/manage.sh](./deploy/manage.sh)**
Добавить команды для управления версиями:
- **`deploy <SYMBOL> --version <TAG>`**:
    1. Найти путь к файлу в `registry.json` по тегу.
    2. Скопировать выбранный `.onnx` и обновить `metadata.json`.
- **`rollback <SYMBOL>`**: Быстрое переключение на предыдущую успешную запись в реестре.

### **5. Тестирование и Тесты**
- **Integrity Test**: В [./tests/risk_gates.rs](./tests/risk_gates.rs) симулировать повреждение файла модели (дописать 1 байт) и убедиться, что бот блокирует запуск.
- **Rollback Test**: Выполнить деплой версии `v2.0`, затем команду `rollback` и проверить, что хэш модели в логах вернулся к `v1.0`.

---

## **Аргументация (согласовано с Grok):**
1. **Per-bot Isolation**: Реестр моделей `registry.json` должен быть свой у каждого бота. Это позволяет разным токенам использовать разные архитектуры (Трансформеры vs MLP) без конфликтов в общем конфиге.
2. **Hash-first Safety**: Сравнение хэша в Rust-коде — единственный надежный способ защиты от "битых" файлов при деплое или случайной подмены модели.
3. **Metadata-driven Normalization**: Параметры Z-score нормализации являются частью обучения модели. Их жесткое кодирование в Rust — главная причина расхождения Backtest/Live. Хранение их в `metadata.json` решает эту проблему.
4. **No Redundancy**: Удалено хеширование конфига из реестра моделей, так как задача [184](./docs/184-infra-config-versioning-and-audit.md) уже решает этот вопрос через аудит самого `config.toml`.

**Gemini, твоя задача — внедрить "пограничный контроль" для моделей. Мы должны быть уверены в каждом байте весов перед началом торгов.**
